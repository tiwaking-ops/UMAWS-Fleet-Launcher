1. What Is This Project

Core Purpose

UMAWS Fleet is an agentic coding orchestration system. It lets a single operator supervise multiple AI coding agents (Claude, OpenCode, Kilo, Cline, Pi, etc.) running in isolated git worktrees, with automatic recovery, quota-aware scheduling, and a formal merge queue that only promotes work that passes acceptance tests.

Think of it as a project conductor: you define tasks in a briefing, the system dispatches agents to work on them in isolated sandboxes, collects evidence that work is correct, and merges only verified changes into your repository. The system runs unattended and recovers from failures automatically.

Key Capabilities

Capability Description
Multi-agent dispatch Runs up to 100 concurrent agents across 6+ CLI profiles (hermes, kilo, cline, pi, opencode, fake)
Worktree isolation Each task gets an isolated git worktree; work never pollutes the main tree until promoted
Oracle-based verification Accepting oracles decide — human claims are not evidence; exit codes and output files are
Recovery ladder (L0–L4) Automatic retries with exponential backoff, model-swapping resume, fresh sessions with handoff notes
Quota-aware scheduling Hierarchical quota engine (QuotaGate) tracks RPM, TPM, RPD per provider with timezone-aware resets
Serial merge queue One merge at a time on the main tree; the gate runs on the tree that becomes canonical
Audit trail Append-only hash-chained JSONL event log; every state change is an auditable event

Origin Story

This project originated as small utility projects that were combined into a pilot (P-01). It evolved from a project management system into an agentic coding harness through 14 commits (as of v1.0), with contributions from multiple AI agents (Claude Code, OpenCode, Claude Web) and a human operator. The system has reached Tier A (Foundation) with a working Fleet.

2. Quick Start Guide

Prerequisites

  • Python 3.12 (3.12.10 recommended)
  • Git (any recent version)
  • Windows 10/11 (native platform; Unix compatibility maintained)
  • At least 2GB free RAM (configurable via max_free_ram_mb in agents.toml)

Installation

<!-- From the project root -->
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m pip install fastapi uvicorn httpx tzdata pytest

Initialize the Kernel

pmk init

This creates the .pm/ directory structure: the event log, the pinned constitution and policy, the views, and the first event.

Start the Console

.\start.ps1
# Or alternatively:
\.venv\Scripts\python.exe -m console.app

The Console binds to http://127.0.0.1:8765. Open it in your browser. By default, dispatch is PAUSED — press the "Run" button to start dispatching tasks.

Run a Demonstration

.\.venv\Scripts\python.exe pilot/demo_one_click.py

Runs the complete lifecycle (brief → PDD → tasks → claim → worktree → spawn → oracles → evidence bundle → merge queue → close-check → DONE) against the fake CLI. Finishes with state: DONE, a clean sentinel, and a verifying chain.

Stop-the-line: Dispatch starts PAUSED (D-A2 decision). You must explicitly unpause by pressing Run in the Console, running pmk dispatch run, or setting a config flag. This prevents accidental agent launches.

3. Architecture Overview

Operator --- browser ---> Console (FastAPI, 127.0.0.1:8765) | v umaws app process Conductor lifecycle, wakes the Overseer Dispatcher selects a profile, claims a task Adapters hermes | kilo | cline | pi | opencode | fake Harness worktree, order file, oracles, evidence pmk.api the Kernel: the only writer of state

Three Layers

Kernel src/pmk/ — Sole Writer of State

The Kernel manages an append-only hash-chained JSONL event log in .pm/events/. It rebuilds State and Views from the log. Agents never write to .pm/ directly — they use the pmk CLI or pmk.api (Invariant I2).

  • Standard library only — no external dependencies in src/pmk/
  • All state mutations go through Kernel.record_event() — never write to .pm/ directly
  • Hash chain maintained in EventLog with torn-tail detection and repair

Fleet src/fleet/ — Process Supervision

The Dispatcher assigns tasks to Profiles (agent configurations). The Harness manages Worktrees and Oracles. The Conductor drives the project lifecycle and the merge queue. Fleet state (profile cooling, disable status) is fleet-wide, not per-project.

Console src/console/ — FastAPI View Layer

A thin FastAPI wrapper over pmk.api and FleetState. Provides seven tabs and live SSE updates. Binds to loopback only (127.0.0.1) for security.

QuotaGate src/quotagate/ — Quota Engine

Hierarchical quota engine tracking RPM, TPM, RPD at four scopes (deployment, account, quota_group, provider) with timezone-aware resets. Supports passthrough proxy (M1), failover (M3), and Kernel contract (M5).

Windows platform constraints:
  • Use <file>.lock for file locks — Windows forbids appending to locked data bytes
  • Read JSON/TOML with utf-8-sig to handle PowerShell BOMs
  • Keep worktree paths shallow under work/ to stay under the 260-char limit

9. Merge Queue & Oracles

The Serial Merge Queue

The merge queue processes one lease at a time, in the main tree, so that the gate command runs on the tree that becomes canonical.

Process

1. scope_check() — reject out-of-scope changes
   2. I5 pre-merge check — load evidence bundle, verify no validation_problems()
   3. commit_worktree() — commit ONLY the declared write scope (NOT git add -A)
   4. _cleanup_default_pytest_ini() — remove untracked default pytest.ini if
      incoming branch changes it (runs AFTER commit_worktree, v11 fix)
   5. git worktree add --detach  
   6. git merge --no-ff --no-edit 
   7. Run gate_cmd on the merged tree
      exit 0 -> proceed
      exit != 0 -> MERGE_REFUSED, task goes to REWORK
   8. git merge --ff-only 
   9. Record INTEGRATED event

The pytest.ini Cleanup (T-0009 Fix)

pmk init writes a default pytest.ini to the repo root. When a lease branch also adds pytest.ini, git sees two untracked files and the fast-forward refuses to overwrite, failing the merge.

The v11 fix (commit 9f2dbaa) moved _cleanup_default_pytest_ini() to run after commit_worktree so the branch ref exists and the git diff reveals the incoming change.

Evidence Bundles

An evidence bundle (.pm/evidence/EB-<task>-<fence>/bundle.json) contains:

  • task, fence, base_commit
  • outputs, commands, oracle_results
  • premise_check, budget_used, resolved_models
  • constitution_hash, context_hash
I5 enforcement is two-layer defense: (1) Conductor checks bundle.validation_problems(), (2) Kernel.integrate checks it again, (3) merge.integrate runs the gate.

10. Recovery System

The Recovery Ladder (L0–L4)

L0: Retry (transient NETWORK failures) Same profile, same session, delayed retries Fence UNCHANGED L1: Resume on next profile Resume session on a different profile Requires: adapter supports resume AND model swap Fence UNCHANGED L2: Fresh session with handoff (same worktree) Start fresh session on next profile with handoff note Fence UNCHANGED Triggered by: QUOTA, AUTH, MODEL_GONE, NETWORK, STALL, UNKNOWN, CRASH L3: Revoke lease, bump fence max_restarts_per_task reached, or no profile qualifies Fence BUMPED — task returns to READY L4: Block task attempts.max reached: task -> BLOCKED, queue item for Overseer

Profile Consequences

FailureConsequence
QUOTACooldown: 1 hour, doubles after each failed probe, up to 24h
AUTHProfile DISABLED. Queue item raised.
MODEL_GONEProfile DISABLED. Queue item raised.
NETWORKNo penalty first failure; 3+ providers within 120s triggers circuit breaker
UNKNOWNRetry once; 2+ failures in 10 min → 15-min cooldown
STALLKill process tree; 2+ stalls in 1 hr → 30-min cooldown
CRASHFresh session with handoff note on next profile (L2)

15. For LLM Agents

How This Works When You Are an AI Agent

If you are an AI agent invoked by the UMAWS Fleet, here is what you need to know:

Your Lifecycle

You receive a prompt from a file
--> You work in an isolated git worktree
--> You run oracle commands (acceptance tests)
--> You produce evidence output files
--> You produce a summary
--> The Harness takes over:
    - Records your outputs as an evidence bundle
    - Runs scope checks (are you writing only in your declared scope?)
    - Commits your work to the lease branch
    - Submits to the merge queue (runs the gate command)
    - If the gate passes: your change is merged into main
--> DONE (or REWORK if gate fails)

Key Rules

  • Work only within your declared write scope — paths are prefix-matched, not globbed
  • Run your oracle commands before exiting — these are your acceptance tests
  • Produce all declared evidence files — the Harness checks for them
  • Do not edit .pm/ directly — use the pmk CLI or API
  • Write your summary to a file — do not rely on stdout alone
If your exit code is non-zero, the Dispatcher classifies your failure (QUOTA, AUTH, MODEL_GONE, NETWORK, STALL, UNKNOWN, CRASH) and applies the recovery ladder. You may be retried, resumed, or replaced — all automatically. Your briefing is the canonical handover document.
